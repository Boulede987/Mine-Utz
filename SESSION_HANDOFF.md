# Session handoff — 2026-08-21 — a third construction-quality fix tried, also disproven; a fourth caught at design time before any code shipped

**New session.** User asked for a state-of-things report (shape/size/retry complaints on the live game), then a plan to continue the construction-quality thread cont.9 paused on. Scope explicitly agreed with the user up front: worldgen-core spike only, no live-path (`SeedRegionCache`) changes, region-edge organic shaping stays deferred.

**Attempt 4 (design-only, never implemented)**: the plan's chosen direction was owned conditioning points — scatter interior conditioning points (as in the already-rejected `InteriorStructuralScatter`), but this time have each real node explicitly absorb/own nearby conditioning points' Voronoi cells instead of leaving them unclaimed, via a "collect each member's own fan, drop petals whose far side shares the same owner, chain the survivors into one loop" mechanism. A dedicated design pass validated the basic pairwise edge-cancellation fact algebraically, but working through the N-member case by hand before writing any code found a real, common (not rare-edge-case) failure mode: at any triangle `{o, p, X}` where a real node `o` and a conditioning point `p` it owns share an edge, AND both are also Delaunay-adjacent to the same externally-owned vertex `X`, the cancellation rule leaves that triangle's corner with TWO surviving outgoing boundary edges and zero incoming — a branch point, not a simple polygon vertex. That silently breaks the one-simple-loop assumption every downstream check (`PatchNegotiator`'s self-intersection/shoelace-area, `PatchRasterizer`'s point-in-polygon) relies on — the same bug class as this pipeline's own earlier, painfully-debugged self-intersection defect, just not yet triggered because no code was written. Caught and abandoned at the design stage, not measured in the field.

**Attempt 5 (implemented, measured, reverted)**: pivoted to something much smaller in scope, to sidestep attempt 4's entire correctness-risk class — a bounded per-corner clamp. Leave a triangle's circumcenter untouched when it's already inside the triangle (the common, healthy case); only for a corrupted (outside) one, clamp its barycentric coordinates to `>= 0` and renormalize, guaranteeing it lands inside the triangle. No new points, no ownership graph, no hole/branch-point risk class at all — the smallest possible intervention. Implemented in `PatchMesh.build` (one call-site change plus a new private helper), full `./gradlew :worldgen-core:test` suite passed unchanged.

Every quality metric got WORSE, not better, despite the fix being deliberately the most conservative, least-invasive option tried yet. Reverted cleanly (`PatchMesh.java` is back to the original unconditional `Circumcenter.of` call); the attempt and its real numbers are recorded in that class's own doc comment, same "don't repeat this without new data" convention already used for the centroid and ownership attempts.

**Update, same session — user asked to actually diagnose the regression rather than leave it as an untested theory.** Confirmed numerically, not just reasoned about: wrote a standalone check computing a synthetic obtuse triangle's raw circumcenter vs. its barycentric-clamped position. The raw circumcenter sat exactly 170.85 units from ALL 3 vertices (the defining property — a circumcenter is the UNIQUE point simultaneously equidistant from a triangle's 3 vertices, which is exactly what makes connecting adjacent circumcenters reconstruct a true, gapless Voronoi diagram). The clamped version sat 59.45 and 7.21 units from the two vertices sharing the edge it's supposed to help bound — nowhere near equal, and pathologically close to one specific seed. Further: the clamp doesn't degrade gracefully with obtuseness — it projects toward whichever single vertex the triangle was most obtuse against, so the WORSE the triangle, the CLOSER the clamped corner crowds that one seed's own polygon boundary, producing a near-degenerate pinch right at that seed's center (feeding thin-neck/isolated-fragment counts) while the broken equidistance opens real gap slivers neither neighboring patch claims (feeding the fallback count). This is the SAME root cause as the earlier centroid-swap failure, not a separate one — centroid just breaks the same equidistance property for every corner instead of only the corrupted ones. Real implication: any fix that moves a corner away from the exact circumcenter is structurally fighting this property, which retroactively also explains why centroid swap failed and suggests owned-conditioning-points (never implemented, killed by the branch-point bug) was actually reaching in the right direction — better point placement upstream to avoid creating obtuse triangles in the first place, rather than any post-hoc corner correction. The other real option, not attempted: stop sharing one corner per triangle across all 3 incident patches for pathological triangles specifically (give each affected edge its own point, each exactly on its own true bisector) — a bigger structural change to `PatchMesh`'s canonicalization scheme.

**Where this leaves the construction-quality thread**: FOUR attempts now (centroid swap, unowned interior scatter, owned/merged interior scatter, bounded corner clamp) have all failed — three measured in the field, one caught at design time — and for the first time this session, a SINGLE underlying reason is understood to explain three of the four (centroid, clamp, and — retroactively — likely part of why plain unowned scatter also struggled): exact multi-way equidistance is required for gapless tiling, and nothing short of the true circumcenter has it. # Session handoff — 2026-08-18 (cont. 8) — the "obvious" construction-quality fix, tried and cleanly disproven

**Eighth update, same session.** User: "go for the deeper fix" (construction-time geometry quality, not another move-time check — see cont. 7's closing note).

**The hypothesis**: `PatchMesh` builds each boundary corner from a Delaunay triangle's {@code Circumcenter} — mathematically the correct way to build a true Voronoi dual, but an obtuse triangle's circumcenter can land arbitrarily far from the triangle itself, even outside the whole triangulation. Real seed points here are irregularly spaced (CSP-placed biome seeds, not a grid), so obtuse triangles are common. Swapped to the triangle's CENTROID instead — always inside its own triangle by construction, eliminating wild excursions outright.

**Result, real 9-region export, before vs. after**: round-0 `thinNeck=true` prevalence DID improve as predicted (55.7% → 44.3%, continuing the trend from cont. 7's own fix) — but `PatchRasterizer`'s nearest-centroid fallback rate more than TRIPLED (16,699 → 55,197 cells across the export), regressing almost every region, not just the sparse ones. **Reverted.**

**Why, understood clearly, not just "it got worse"**: a circumcenter-based Voronoi dual has a real mathematical guarantee — the resulting cells tile the WHOLE plane with zero gaps, by definition (each cell = "closer to this site than any other"). A centroid-based approximation shares the same corner-sharing/no-disagreement structure (same triangulation, same shared point ids) but loses that completeness guarantee entirely - there is no theorem saying centroid-built cells don't leave gaps between neighbors, and empirically they do, badly. The two candidate fixes traded directly against each other: better LOCAL geometry (fewer construction-time necks) vs. worse GLOBAL coverage (more of the map never touches a real negotiated shape at all, falling to crude nearest-centroid guessing) — and the coverage property is clearly the more important one to protect.

**Where this leaves things**: the construction-quality problem (many nodes starting with SOME geometric irregularity before negotiation even runs) is real and still open. Any real fix needs to preserve circumcenter's tiling-completeness guarantee, not trade it away — e.g. adding more DENSE interior structural points (not just ring density, which cont. 6 already fixed for the cold-start case specifically) so triangles are less likely to be pathologically obtuse in the first place, rather than changing the corner-position formula itself. Not attempted yet.

**Current best-known state, confirmed after the clean revert**: 159/52/125 (total/isolated/thin fragments), ~25s solve time, full test suite passes — same numbers as the end of cont. 7.

**Honest assessment for next session**: this fix is defensible on correctness grounds alone (the neck check now actually measures what it claims to, instead of mostly grandfathering itself into uselessness) even though the aggregate isolated-cell count didn't clearly improve. The construction-time defect itself (why so many nodes start with SOME kind of geometric irregularity at round 0, whether a genuine neck or not) is still unsolved — detecting it better doesn't repair damage that already happened before detection runs. # Session handoff — 2026-08-18 (cont. 5) — found and fixed the REAL cause of straight edges, tuned two more levers with real data

**Fifth update, same session, user pushed back again**: "not good enough... way more variation... several straight edges still." Looked at the actual regions.png (not just fragment counts this time) and found a much bigger bug than expected: `PatchNegotiator.relax` **returned the instant every node's own MINIMUM area was satisfied** — before this session's own `MAX_NEGOTIATION_ROUNDS` raise to 800 could ever matter for a fast-converging patch. One region in the export solved in 136ms; nowhere near enough rounds for wobble/smoothing to develop an organic look. The 800-round budget only ever helped patches that struggled - every easy one locked in as a barely-wobbled, near-straight shape the moment it hit its minimum.

**Fix 1 - removed the early return.** `relax` now always runs the full `maxRounds` budget; hitting the minimum is logged but no longer stops anything (growth toward the larger TARGET, wobble, and smoothing all keep running). Confirmed by direct image comparison: shapes visibly more organic (the region-(1,1) savanna blob went from an angular wedge to a genuinely rounded shape).

**A real correctness gap this exposed, caught by the unit suite**: once wobble runs for the FULL budget instead of stopping at convergence, and wobble's own strength INCREASES as urgency drops near target, a node could get wobbled back BELOW its own minimum again after first reaching it — nothing was checking for that. Fixed by extending the existing three-way `ShapeState` verification (crossing/neck) with a third independent bit: `belowMinimum`, grandfathered the same way as the other two (a node already below minimum isn't blocked from moving further; only a node that HAD reached minimum is protected from being pushed back under it).

**A second real, measured regression from fix 1 alone**: full-strength wobble for the entire budget, not just a few rounds, gave the boundary many more chances to wander into locally-thin configurations — real 9-region fragment count went UP (200 → 222 total, 70 → 106 isolated) even though the shapes looked visibly better. **Fix 2**: added `wobbleAnnealFactor` — wobble strength now linearly decays from full at round 0 to 25% by `maxRounds`, so early rounds still get full organic variety while late rounds mostly let smoothing settle an already-decent shape instead of continuing to gamble on new ones.

**Net result, same real 9-region export, all three fixes together**: 338 → **155** total fragments (was 200 after last session's neck-only fix), 153 → **42** isolated single cells (was 70), 153 → **122** thin components (was 164, now actually better than the ORIGINAL baseline). Solve time unchanged (~22s). Full `./gradlew :worldgen-core:test` passes. This is the best result across every metric simultaneously so far, not a tradeoff.

**Tried and explicitly rejected, with real data**: an absolute (not just relative) floor on the neck-clearance check, meant to close the remaining diagonal-ribbon-of-isolated-cells case (a genuinely continuous but sub-cell-thin diagonal strip that scatters into single-cell fragments under 4-connected counting). Measured WORSE at both 3.0 macro-cells (169/64/137) and 1.5 (156/53/124) than no floor at all (155/42/122) — same over-blocking failure mode as a too-high relative fraction: it blocks legitimate growth near naturally-tight corners on small patches. Reverted. The diagonal-ribbon case is real but not fixable by tightening this particular check further — most likely needs either a `PatchRasterizer` fix (point-in-polygon's ray-casting test is a known-fragile case near vertices; ~41 of the remaining isolated cells have NO same-biome neighbor even diagonally, pointing at rasterization, not shape) or a genuinely different check (true segment-to-segment corridor width, not point-to-point).

# Session handoff — 2026-08-18 (cont. 4) — thin-neck check: real, partial fix, precisely diagnosed remainder

**Fourth update.** User looked at cont. 3's export critically again and pushed back hard: "shape quality already fails hard... massive spikes, isolated cells, I'm not sure the plains size is legal, there are thin stripes of plains." Instead of eyeballing another PNG, added a JSON export (`ShapeExportCli`/`JsonExporter` already existed for the export, just wasn't wired to write regions.json - now it is) and a Python flood-fill script that counts actual connected same-biome fragments per region. **The complaint was right, and worse than it looked**: 338 total fragments across 9 regions (should be roughly one per free patch, ~72-81), 153 of them a single isolated macro-cell, 153 thinner than half their biome's own declared minimum width.

**Root cause**: `PatchNegotiator` only ever checked for self-crossing (`isSelfIntersecting`). A long thin finger of boundary never crosses itself — every point on it agrees with its own immediate neighbors — so it read as "simple" by every check this class had, right up until `PatchRasterizer` turned it into scattered single-cell debris. This is the old pixel-level pipeline's "no 1-wide neck" (`MeshCohesion`) problem, with zero equivalent in the new shape-first pipeline until now.

**Fix**: added `hasThinNeck` — flags a polygon where two NON-adjacent boundary points have pinched closer together than `NECK_CLEARANCE_FRACTION` (tuned to 0.5) of that node's own average edge length. Wired into both places that already verify a move before keeping it (the ordinary per-point loop and the escalation/steal path), same "was clean before, don't newly break it" pattern already proven for the crossing check.

**A real bug in the first version of this fix, caught by the test suite (not a visual check this time)**: combined both checks into one `isShapeBroken` OR flag. A node with a thin neck (but no crossing) then counted as "already broken," which meant it lost its CROSSING protection too — a move could freely introduce a brand-new self-intersection on it, since the neck defect grandfathered the move through. Fixed by tracking the two defects as independent booleans (`ShapeState` record) — each must grandfather on its own, never mixed.

**Tuned `NECK_CLEARANCE_FRACTION` across a real range, not guessed**: 0.3 → 191/72/155 (total/isolated/thin), 0.5 → 200/70/164, 0.75 and 1.0 both **regressed** (297/111/258 at 1.0) and broke the growth-shortfall unit test — a stricter neck threshold blocks legitimate growth moves on normal many-sided convex corners too (points two steps apart around a real corner can legitimately sit closer than one full edge length), so patches got stuck further from their targets and left MORE gaps for the rasterizer's nearest-centroid fallback to fill unpredictably. # Session handoff — 2026-08-17 (cont. 2) — shape-first geometry Step 0: two more real bugs, fixed

**Second update.** User kept looking critically at each fix instead of accepting "it's an improvement" — correctly, each time. After the self-intersection fix below, user reported the rasterized output was STILL bad: "still the straight lines and single cells." Two more real bugs found and fixed, both confirmed with a direct look at the actual exported image, not just numbers:

1. **Unbounded growth** — confirmed via a per-round trajectory log (new: `PatchNegotiator.relax` now logs an area snapshot every 20 rounds, not just at the end): one real node grew `9,049 → 14,016,770` in continuous, ACCELERATING steps over 300 rounds, well past the point its own growth pull should have been zero. Any one point could wobble far past its own neighbor's position relative to how close they actually were, guaranteeing incoherent zigzags. This is the exact mismatch `EdgeDisplacement` (the old pipeline's own cosmetic step) avoids by scaling to LOCAL edge length instead. Fixed: wobble amplitude now scales to the average distance to a point's own immediate boundary-loop neighbors (new `PatchNegotiator.loopNeighborPositions`/`distance` helpers), not the whole patch's size. Also added a mild boundary-smoothing pull (`SMOOTHING_FRACTION = 0.2`, pulls a point toward its neighbors' midpoint) as a secondary regularizer — tuned down from an initial `0.3` that actively fought and reversed legitimate growth in the small test grid (a real, deliberately-uneven-target test case), and from `0.1` which passed tests but was visually too weak to matter.
