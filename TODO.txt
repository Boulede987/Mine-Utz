No — the opposite, actually. Two separate steps, each controlling a different thing:

Step 1 (the mesh + the "who can be next to whom" step): Random points get placed on the map, then connected into a triangle mesh — that part IS pretty randomized, just picking rough positions. But then, before any coloring happens, each triangle gets ASSIGNED a biome one at a time, and a triangle is only allowed to get a biome if that biome is legal next to every triangle around it that's already been assigned (checked against the rules you define — like "desert can touch savanna, desert can't touch ocean"). If no legal biome fits, it backtracks and tries something else. This is where "which biomes end up near which" is actually decided and locked in — hard rule, not chance.

Step 2 (growth, the coloring-in step): This only decides the exact SHAPE each already-assigned triangle's biome takes up — the wiggly border line, exactly which square belongs to which patch. It does NOT get to introduce a new neighbor pairing that wasn't already legal — every single square, as it gets colored, is checked against the same rules again. It literally cannot place an illegal touch (that's the "zero illegal adjacencies" guarantee this whole session's testing keeps confirming).

So: which biome families can border each other — fully controlled, hard rule, enforced twice. What's NOT hand-controlled is the exact curve of the border and the rough starting position of each patch — that's what the mesh randomness and the growth competition decide.

IDEA: smarter dead-end pre-check for BiomeGraph (generalize requireEveryLocalNeighborhoodSolvable)

Motivation: real crashes happened because a generated triangle had an impossible
combination of neighbors (no biome legal against all of them at once) - and historically
the only way we found these was by generating an actual world and getting unlucky enough
to hit the bad combination during real play/export. Hunting bugs by luck is a terrible
way to find them.

BiomeGraph.requireEveryLocalNeighborhoodSolvable(maxNeighbors) already fixes this FOR
TODAY'S graph: it's a real, deterministic, exhaustive, offline proof (no world generation,
no luck involved), wired into BiomeGraph.forProduction so an impossible combination fails
the BUILD itself, not a random real-world generation session later. It works by brute
force - checking every literal combination of up to maxNeighbors distinct biomes.

The catch: today's graph only has 6 biomes, so brute-force enumeration is cheap. It won't
stay cheap - a much larger, more realistic biome list makes checking every literal
combination computationally infeasible (this is the "graph check that was rejected for
being impossible" - not impossible in concept, impossible to run exhaustively at real
scale). That's the actual problem this idea solves.

The idea: we don't need to test every combination in every graph. Many concrete
combinations aren't really distinct problems - they're the same structural situation
wearing different biome names. Instead of checking every actual tuple of biomes, abstract
combinations into general "situation types" based on their legality-relationship pattern
(e.g. "K biomes that are pairwise mutually illegal, needing one shared bridge biome" is
one abstract shape/type, regardless of which specific biomes fill it) - then just check
whether the graph contains an instance matching each dangerous type, instead of testing
every concrete instance of it separately.

Could also be framed in terms of proportions/graph properties instead of exact biome
counts - thinking in "types" of combinations instead of the specific biomes we happen to
have. A scale-independent proof technique instead of one that gets combinatorially more
expensive as the biome list grows.

Not started - requireEveryLocalNeighborhoodSolvable(8) is correct and sufficient for
today's 6-biome graph, so there's no urgency yet. Worth building before the real biome
list grows large enough to make brute-force enumeration actually slow/infeasible.
